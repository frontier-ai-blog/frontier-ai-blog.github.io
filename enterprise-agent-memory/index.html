Memory and Context

Designing Memory for Enterprise Agents

What it takes to build simple, effective memory for enterprise agent harnesses.

Kartik Fnu · Applied Scientist II · October 20, 2026

contents~13 min

Persistent notes, structured records, vector search and temporal knowledge graphs all help agents store and recall context from past interactions. In a large enterprise, much of the preference and context worth learning comes both from interactions with agents across applications and from the work people do in those applications: revising documents, discussing decisions in chat, confirming changes by email and handing tasks to colleagues. As that work moves across applications, memory agents need to connect these observations into an understanding of people’s preferences, ongoing projects and recurring workflows. That memory should help whichever agent handles the next conversation follow a preference without another reminder, find the right project material, or drop an assumption that no longer holds. This article explores how to build and maintain that shared understanding without retaining every interaction, and how to tell whether it actually makes the next task easier.

one week · four applicationsAtlas review

PowerPoint. While preparing an Atlas executive review, Maya asks the agent to put decisions before supporting detail.

Teams. The project group says the Atlas forecast must stay marked preliminary until Finance closes the books.

Outlook. Later that week, Priya confirms that Finance has closed the books and the forecast is final.

The following week · Word. Maya asks for the next Atlas review. The agent leads with decisions, uses search to find the finalized forecast, and leaves off the preliminary label. Maya does not have to repeat her preference or explain what changed.

The useful memory in this example is small. It carries Maya’s preference into the next review, keeps the forecast restriction tied to Atlas, and retires that restriction when Finance’s confirmation arrives. It does not need another copy of the deck, chat or email, only enough context to guide the next task and a link back to the evidence when the agent needs to check.

That distinction shapes the design: combine observations across applications, preserve their source and scope, recognize when context no longer applies, and track which conclusions depend on which evidence.

01

The hardest retrieval decisions happen during compression

Memory benchmarks begin with retention. They test whether a system can preserve as much potentially useful information as possible, then update, connect and recover it across long histories. That framing assumes the history remains available and scores the answer, not the operational cost, governance burden or value of retaining everything that made the answer possible.

The benchmark questionGiven everything, can the system find what matters?

The memory-design question starts earlierWhat deserves to remain?

Most of what an agent learns about a person has a short useful life: a task closes, a document ships, a project winds down, a preference is corrected. Information that remains useful months later (who owns a project, what a team decided, or which document is approved) often already lives in the systems where that work is managed. Memory can help agents find and use those sources without keeping a separate copy of the facts. Smaller, scoped memory handles most of the remainder without semantic search over thousands of accumulated facts. For memory to work well, this means preserving a thin layer of durable instructions and working context rather than building another knowledge base. The goal is the smallest memory that still changes the agent's behaviour for the better.

Memory cost is the recurring overhead added to every conversation, not the price of storing a few kilobytes. That overhead includes context assembly, cache writes, semantic queries, ranking, model tokens, consolidation, permission checks and eventual deletion. At just 20¢ memory overhead per conversation, assuming 5 conversations per seat per day × 50,000 seats × 365 days, that's >$15 million a year.

The testInstrument how often a memory older than thirty days is the thing that makes a task succeed. Repeat the measurement at ninety days, six months and one year, separated by memory type. Measure the failures too: stale assumptions, incorrect search filters, unnecessary context and answers produced from something that should already have expired. The retention window should come from those curves, not from how much the underlying store can hold.

02

Three memory types for the enterprise case

Memory literature already provides useful vocabulary along several axes: duration, content, subject and function. Four labels (working, episodic, semantic and procedural) come directly from cognitive memory models and are adopted by agent frameworks such as CoALA. Conversational memory is used for retained dialogue history in systems such as MemGPT; preference memory appears in personalization research such as VARS; and organizational memory comes from a separate organizational-learning literature established by Walsh and Ungson.

Table 1. Sourced memory labels

LabelWhat it usually meansPrior use
WorkingInformation available to the current computation.CoALA
ConversationalThe active exchange and retained history needed to continue it.MemGPT, LongMemEval
EpisodicParticular events or experiences: what happened, when and in what context.CoALA
SemanticGeneralized facts and concepts abstracted from particular events.CoALA
ProceduralReusable skills, methods and ways of performing a task.CoALA
PreferencePersistent representations of how a user wants an agent to choose or respond.VARS
OrganizationalInformation retained from an organization's history that can influence present decisions.Walsh and Ungson

For this enterprise design, we use three durable memory types. They are not supersets of the labels above and do not need a one-to-one mapping. They identify three kinds of information that agents must learn and maintain differently.

Workflow memory is learned over a longer horizon than a single instruction. It comes from comparing trajectories across conversations: where the agent repeatedly takes a wrong turn, where the user redirects it, which sources resolve the task fastest, which handoffs recur and which larger goal connects otherwise separate requests. It is a compact model of how this user's work tends to progress, not a transcript of what happened.

Related reading Persistent, Executable Memory for AI Agents

A related experiment stores procedural knowledge as code that an agent reads, writes, and reorganizes across tasks.

The remaining labels still have clear roles:

  • Working and conversational memory can remain runtime context.
  • Episodic traces can remain temporary evidence used to derive durable records.
  • Artifact is usually a scope, and evidence is provenance attached to a record.

They remain useful concepts without becoming separate top-level types in this design.

03

Every memory type needs a schema

A learned preference needs more than a sentence. Maya’s repeated edits may suggest that she prefers rounded figures in executive presentations but not in audit workbooks. If the agent learns something from a confidential document, that memory must not surface in contexts that lack access to the source; a temporary memory may also need to expire after a few days. A schema makes these boundaries explicit and links each inference to its supporting evidence, so the system knows where it can be used, when to retire it and what to reconsider if its source changes.

The schema answers three groups of questions:

  • Type and scope: what the record is and where it may act.
  • Source and validity: why it is believed and when it stops.
  • Importance, evidence and lineage: whether it deserves attention and what supports or depends on it.

Table 2. Common governance fields, applied by type

scopeThe artifact, task, application, user, team or organization it governsApplying it outside that boundary could change behavior

Let the type decide the fields

A memory type describes how information behaves. Within it, different entities still need different contracts. Below are example schemas for five common memory records.

Records for maintenance, prose for reading

Typed records do not require giving up markdown. The maintained form and the served form have different jobs. Tools write structured records so the system can expire, retract, traverse and audit them. The model reads a compact prose projection because prose carries more meaning per token and is easier to scan. Typed records also create a boundary between what memory means and where it is stored. Sources and storage can change without changing the contracts above them.

04

Dreaming: Night and Day

An agent can collect hundreds of plausible memories in a day. Most are routine activity, duplicates, automated noise or one-off behavior. Save them all and memory becomes an activity log within days: larger, less precise and less trustworthy. Memory has a day shift and a dream shift: by day, the agent collects evidence; at night, it decides what deserves to survive.

Dreaming is the offline pass that turns observation into maintained memory. OpenAI uses the term for background synthesis; here it means comparing a window of experience, updating the typed records that already exist and discarding what should not survive. The delay is essential because hindsight separates an event from a pattern.

A request to lead one deck with decisions belongs to that deck. The same choice across several reviews can become a presentation preference. Repeated requests to show a diff before rewriting can become a procedural memory. An exception for customer-facing material then limits where either may act. Dreaming finds the patterns, adjusts their scope and resolves the conflicts.

Filter before inference

Remove duplicates, no-ops and automated noise before inference, so the model sees a small candidate set rather than the entire day. Use model judgment to decide whether those candidates reinforce a preference, update project context, reveal a workflow or warrant no lasting memory.

What dreaming does

Dreaming is more than summarization. It merges repetition, resolves contradictions, widens or narrows scope, retires expired state and follows dependencies when a source disappears. The operations are finite enough to name.

05

Load by scope, retrieve by need

Memory is useful before the first tool call. At session start, load the user’s general preferences and working context, along with memory scoped to the application they are using. Keep everything else visible through a compact index and fetch it only when the task crosses into that scope.

Deciding what to load is less about eager versus lazy retrieval than about certainty versus speculation.

  1. Load the user, current projects, promoted preferences and anything attached to the open artifact.
  2. Expose the names and locations of other memory without loading the payload.

Eager on the certain, lazy on the speculative.

A compact projection also gives caching something stable to reuse. Root memory changes rarely. Artifact memory changes with the document. The volatile tier should therefore stay the smallest.

Use the tools the harness already knows

Memory should look like a small filesystem, not a new tool ecosystem. Let the agent use the glob, grep, read and write tools the harness already provides. memory_read and memory_write are the policy-enforcing abstraction behind those existing read and write operations when the path points into memory; the model does not see them as separate tools.

  • Read boundary. A shared memory store does not imply a shared view. Every entrypoint receives its own projection of the memory tree, filtered by application, artifact, user, source permissions and policy. App A can read promoted user context and App A memory; App B remains invisible unless the task and policy explicitly require cross-application access. Parent folders are not automatically readable merely because a child is mounted.
  • Write boundary. Agents can create, update and delete memory within the scope they are operating in, but they cannot change a sibling, parent or team scope unless that capability is explicitly granted. memory_write enforces both the operation and its scope. Consolidation performs promotion only after checking evidence, provenance and permission inheritance.

This keeps a convenient filesystem interface without turning every agent into an administrator of the entire memory store.

Reload memory after context compaction

When a conversation approaches the agent harness’s context limit, the harness may compact it into a shorter summary so the session can continue. That summary can preserve a remembered fact while losing its source, scope or validity. When rebuilding the context, reload the maintained memory rather than treating the conversation summary as its replacement.

In this design, the system prompt, tools prompt and memory projection form a frozen prefix when the context is built. Compaction logic can differ across harnesses. When the harness rebuilds the context, it reads the maintained memory again and injects the current projection rather than relying on memory carried through the summary.

A working exampleClaude Code loads broad instruction files at session start, loads narrower path-scoped files when matching files are accessed, and re-reads project-root instructions after compaction. The enterprise version uses different scopes but follows the same pattern: deterministic loading for known context, progressive disclosure for the rest.

06

Memory narrows the query, search grounds the answer

Search knows what the organization has. Memory knows which part of it the user probably means.

When a request is underspecified, memory shapes the query rather than answering it. Enterprise search already uses permissions, recency, organizational context and user activity to rank results. Memory adds the working context learned across sessions: the active project, current collaborators, open artifacts and alternatives that are no longer relevant. It turns “the review” into “the FY26Q3 QBR with Priya and Sam”, a narrower question for an already capable search system.

What memory supplies is a set of filters, not content: the entity set to disambiguate against, the vocabulary the organisation actually uses, the recency window that matters, the collaborators worth restricting to, the artifacts already open. Each is a precision gain on a problem that is otherwise recall-bound, and each hop saved is a second of latency and a few thousand tokens of search payload that never enter the window.

Search wins outright in three cases:

  1. When the source of truth must be a governed document rather than a projection of one.
  2. When the question is about anything other than the person.
  3. When the task is genuinely newer or older than what memory holds, at which point memory contributes noise with high confidence attached.

The failure mode to design against is the middle case: memory holds something plausible and the agent stops there.

07

Evaluate the agent, not the memory

The baseline is the same agent with memory off, under comparable latency and cost constraints. Memory succeeds only if the agent completes more tasks, uses fewer turns and tools, asks fewer unnecessary questions and makes fewer stale assumptions.

Measure two systems separately. Memory generation asks whether the agent forms, updates and removes good records. Memory usage asks whether those records improve later work. A system can retrieve its memories perfectly while maintaining the wrong ones.

Table 4. What to measure, and against what

AreaMeasureBaseline
UsageTask success, tool calls, turns and clarifying questionsSame agent, memory disabled
GenerationMerge, promotion, correction and expiry precisionHand-labelled synthetic day
AbstentionUnsupported answers caused by plausible memoryNo-memory or sparse-memory condition
Scope costTokens and task impact by root, application and artifact tierRemove one tier at a time
RetentionBenefit and stale-memory failures by record ageThirty-day cutoff (see §01)
Cold startDays until memory produces measurable benefitDay zero, empty store

Generation and usage fail independently.

  1. Evaluate generation against a labelled synthetic day: did the system merge, promote, correct and expire the right records?
  2. Evaluate usage on real tasks: did those records improve the agent’s decisions and reduce unnecessary work?

Evaluate both the memories the system forms and the work they help agents complete; retrieval accuracy alone does not establish either. Test whether memory reduces unnecessary work while respecting scope, access and expiry, and whether agents avoid relying on it when the evidence is insufficient.
