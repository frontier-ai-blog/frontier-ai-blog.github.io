Agent Memory Architecture

The Enterprise Memory Iceberg: What Retrieval Benchmarks Don’t See

Learnings from building the compression, governance and consolidation layers beneath agent recall.

Kartik Fnu · Applied Scientist II · September 2026

contents~13 min

Files, vector stores and temporal graphs all solve a useful problem: helping an agent recover context it would otherwise forget. Inside a company, retrieval is only the beginning. The harder problem is carrying what an agent learns across applications without losing where it came from, where it applies, or when it stops being true.

one memory · four entrypointsone week

PowerPoint. Maya tells the agent to lead executive reviews with decisions.

Teams. The project group marks the Atlas forecast provisional until Finance closes the books on Friday.

Outlook. Priya confirms the final numbers by email.

One week later · Word. Maya asks for the next Atlas review. Memory carries the preference and project context across applications, recognizes that the provisional restriction has ended, and uses search to retrieve the final forecast.

Those systems can recover every artifact in the sequence. What they do not maintain are the relationships between them: which information should carry forward, where it may act and when it should stop. Maya’s preference should travel, the Atlas restriction should remain project-scoped, and Priya’s confirmation should end it. Memory preserves those relationships and rules, not another copy of the work.

Enterprise memory is not another knowledge base. It is a thin, governed layer over the systems the organization already maintains, holding what working with a person taught the agents and no authoritative system recorded.

01

The hardest retrieval decisions happen during compression

Memory benchmarks begin with retention. They test whether a system can preserve as much potentially useful information as possible, then update, connect and recover it across long histories. That framing assumes the history remains available and scores the answer — not the operational cost, governance burden or value of retaining everything that made the answer possible.

The benchmark questionGiven everything, can the system find what matters?

The memory-design question starts earlierWhat deserves to remain?

Most of what an agent learns about a person has a short useful life: a task closes, a document ships, a project winds down, a preference is corrected. The rare facts that genuinely matter six months later — who owns what, what was decided, which document is authoritative — are usually already held, and held better, by company systems. Smaller, scoped memory handles most of the remainder without semantic search over thousands of accumulated facts. For memory to work well, this means preserving a thin layer of durable instructions and working context — not building another knowledge base. The goal is the smallest memory that still changes the agent's behaviour for the better.

Memory cost is not the price of storing a few kilobytes. It is the recurring overhead added to every conversation: context assembly, cache writes, semantic queries, ranking, model tokens, consolidation, permission checks and eventual deletion. The back-of-the-envelope calculation of just 20¢ memory overhead per conversation, assuming 5 conversations per seat × 50,000 seats, that >$15 million a year.

A retrieval system is judged on what it can find. A compression system is judged on what it can throw away without changing the output — and on what breaks when it throws away too much.

The testInstrument how often a memory older than thirty days is the thing that makes a task succeed. Repeat the measurement at ninety days, six months and one year, separated by memory type. Measure the failures too: stale assumptions, incorrect search filters, unnecessary context and answers produced from something that should already have expired. The retention window should come from those curves, not from how much the underlying store can hold.

02

Three memory types for the enterprise case

Memory literature already provides useful vocabulary along several axes: duration, content, subject and function. Four labels — working, episodic, semantic and procedural — come directly from cognitive memory models and are adopted by agent frameworks such as CoALA. Conversational memory is used for retained dialogue history in systems such as MemGPT; preference memory appears in personalization research such as VARS; and organizational memory comes from a separate organizational-learning literature established by Walsh and Ungson.

Table 1 — sourced memory labels

LabelWhat it usually meansPrior use
WorkingInformation available to the current computation.CoALA
ConversationalThe active exchange and retained history needed to continue it.MemGPT, LongMemEval
EpisodicParticular events or experiences: what happened, when and in what context.CoALA
SemanticGeneralized facts and concepts abstracted from particular events.CoALA
ProceduralReusable skills, methods and ways of performing a task.CoALA
PreferencePersistent representations of how a user wants an agent to choose or respond.VARS
OrganizationalInformation retained from an organization's history that can influence present decisions.Walsh and Ungson

For this enterprise design, we use three durable memory types. They are not supersets of the labels above and do not need a one-to-one mapping. They identify three kinds of information that agents must learn and maintain differently.

Workflow memory is learned over a longer horizon than a single instruction. It comes from comparing trajectories across conversations: where the agent repeatedly takes a wrong turn, where the user redirects it, which sources resolve the task fastest, which handoffs recur and which larger goal connects otherwise separate requests. It is not a transcript of what happened. It is a compact model of how this user's work tends to progress.

Working and conversational memory can remain runtime context. Episodic traces can remain temporary evidence used to derive durable records. Artifact is usually a scope, and evidence is provenance attached to a record. They remain useful concepts without becoming separate top-level types in this design.

03

Every memory type needs a schema

document openedthree recommendations

Maya opens a new quarterly-review document. Before she asks, the agent recommends:

Add margin beside revenue. Maya accepted this layout in three previous quarterly reviews.

Ask Priya to review the assumptions. In her Monday email, Priya confirmed that she owns the margin review.

Keep the Atlas figures marked preliminary. Finance expects to close the books on Friday.

The model can read three lines of prose. The system maintaining them needs to know where each recommendation applies, what supports it and when it should stop appearing.

Similarity is not a memory policy. A project, a person, a task, a preference and a workflow may all mention the same document. They are still different objects because they change in different ways. Maintained memory needs a typed schema.

Type says what the record is. Scope says where it may act. Source says why it is believed. Validity says when it stops. Importance says whether it deserves attention. Evidence and lineage appear when the record was inferred or derived.

Embeddings answer: what looks related? Typed ranking answers: what should influence this recommendation now? Filter for scope and validity. Authority is not confidence: one stated instruction outranks repeated inference. Rank the remaining records by importance, evidence, recency and semantic fit.

Table 2 — common governance fields, applied by type

FieldAnswersRequired when
sourceWhere this information came fromThe record depends on an observation, instruction or enterprise artifact
assertionWhether it was stated, observed or inferredAuthority changes how quickly the record may be applied or promoted
validThe time window or event boundaryThe information can expire, be superseded or become unsafe when stale
scopeThe artifact, task, application, user, team or organization it governsApplying it outside that boundary could change behavior
evidenceThe observations supporting a learned patternThe record is inferred rather than directly stated
derived_fromThe upstream records or artifacts it depends onRetraction, deletion or recomputation must propagate

Let the type decide the fields

A memory type describes how information behaves. Within it, different entities still need different contracts. The five below are enough to maintain the recommendation example without pretending to be a complete enterprise ontology.

Records for maintenance, prose for reading

Typed records do not require giving up markdown. The maintained form and the served form have different jobs. Tools write structured records so the system can expire, retract, traverse and audit them. The model reads a compact prose projection because prose carries more meaning per token and is easier to scan.

Separate the contract from the implementation

Typed records create a boundary between what memory means and where it is stored. Sources and storage can change without changing the contracts above them.

04

Dreaming keeps memory from becoming noise

An agent can collect hundreds of plausible memories in a day. Most are routine activity, duplicates, automated noise or one-off behavior. Save them all and memory becomes an activity log within days: larger, less precise and less trustworthy.

Dreaming is the offline pass that turns observation into maintained memory. OpenAI uses the term for background synthesis; here it means comparing a window of experience, updating the typed records that already exist and discarding what should not survive. The delay is essential because hindsight separates an event from a pattern.

One rename belongs to a workbook. The same rename across three workbooks earns promotion to a spreadsheet preference. An explicit exception for customer forecasts then limits where it may act. Dreaming finds the pattern, widens its scope and resolves the conflict.

Filter before inference

Most signals do not require a model decision. Duplicates, no-ops, automated messages and activity with no human decision or action can be removed deterministically. The model should see a small candidate set, not the entire day.

The remaining work requires judgment: whether observations reinforce an existing preference, change a project, reveal a workflow or mean nothing durable. This is the difference between collecting history and maintaining memory.

What dreaming does

Dreaming is more than summarization. It merges repetition, resolves contradictions, widens or narrows scope, retires expired state and follows dependencies when a source disappears. The operations are finite enough to name.

A stated correction is not another observation. It is an override. If Maya says, “Stop shortening my email subjects,” the next dream must not weigh that instruction against twelve earlier acceptances. Explicit memory actions belong in an append-only diary so the same history cannot recreate what the user removed.

Removal is part of the same pass. When a source is deleted, a person leaves or a retention window closes, dreaming follows source and derived_from to anything that depended on it. Otherwise the next pass can infer the deleted memory again.

A bad retrieval damages one turn. A bad merge, promotion or inference changes what every later session believes. Dreaming is where memory becomes smaller — and where it becomes safe to trust.

05

Load by scope, retrieve by need

Memory is useful before the first tool call. Root memory and the active application are already known when a session begins, so load them. Keep everything else visible through a compact index and fetch it only when the task crosses into that scope.

This is not eager versus lazy retrieval. It is certainty versus speculation. Load the user, current projects, promoted preferences and anything attached to the open artifact. Expose the names and locations of other memory without loading the payload. Eager on the certain, lazy on the speculative.

A compact projection also gives caching something stable to reuse. Root memory changes rarely. Artifact memory changes with the document. The volatile tier should therefore stay the smallest.

Compaction is a reload boundary

Compaction summarizes a conversation, not a memory contract. It preserves the gist and drops fields such as source, assertion and valid because they are not narratively important. The result is a plausible sentence with no authority or end condition.

Treat compaction as a reload boundary. Exclude memory from the summary, then regenerate its prose projection from the maintained records. The required fields are reconstructed rather than trusted to survive.

A working exampleClaude Code loads broad instruction files at session start, loads narrower path-scoped files when matching files are accessed, and re-reads project-root instructions after compaction. The enterprise version uses different scopes, but the pattern is the same: deterministic loading for known context, progressive disclosure for the rest.

06

Memory narrows the query, search grounds the answer

Search knows what the organization has. Memory knows which part of it the user probably means.

When a request is underspecified, memory shapes the query rather than answering it. Enterprise search already uses permissions, recency, organizational context and user activity to rank results. Memory adds the working context learned across sessions: the active project, current collaborators, open artifacts and alternatives that are no longer relevant. It turns “the review” into “the FY26Q3 QBR with Priya and Sam” — a narrower question for an already capable search system.

What memory supplies is a set of filters, not content: the entity set to disambiguate against, the vocabulary the organisation actually uses, the recency window that matters, the collaborators worth restricting to, the artifacts already open. Each is a precision gain on a problem that is otherwise recall-bound, and each hop saved is a second of latency and a few thousand tokens of search payload that never enter the window.

Search wins outright in three cases: when the source of truth must be a governed document rather than a projection of one; when the question is about anything other than the person; and when the task is genuinely newer or older than what memory holds, at which point memory contributes noise with high confidence attached. The failure mode to design against is the middle case — memory holds something plausible and the agent stops there.

07

Evaluate the agent, not the memory

The baseline is the same agent with memory off, under the same latency and cost constraints. Memory succeeds only if the agent completes more tasks, uses fewer turns and tools, asks fewer unnecessary questions and makes fewer stale assumptions.

Measure two systems separately. Memory generation asks whether the agent forms, updates and removes good records. Memory usage asks whether those records improve later work. A system can retrieve its memories perfectly while maintaining the wrong ones.

Table 4 — what to measure, and against what

AreaMeasureBaseline
UsageTask success, tool calls, turns and clarifying questionsSame agent, memory disabled

AbstentionUnsupported answers caused by plausible memoryNo-memory or sparse-memory condition

Generation and usage fail independently. Test generation with a synthetic day whose correct merges, promotions, corrections and expiries are labelled in advance. Test usage on real tasks. Production logs rarely reveal what the memory should have been after the fact.

Retrieval benchmarks remain useful, but they cover only part of the system. They rarely test concurrent writers, scope promotion, event-bound expiry, access inheritance, deletion propagation or whether memory reduces enterprise-search work. Aggregate accuracy can also hide the tradeoff between recalling more and knowing when not to answer.

What made Maya’s Thursday easier was not another copy of the deck. It was the small amount the agents had learned about her work: who reviews margin, which project is winding down, how she names fiscal columns and when she wants a diff instead of a rewrite. If those records reduce work without escaping their scope or surviving past their evidence, memory is helping. Everything else the organization already knows.
