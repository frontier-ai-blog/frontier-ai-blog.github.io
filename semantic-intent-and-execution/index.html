Agent Architecture

Separating Semantic Intent from Execution in Knowledge-Work Agents

The right abstraction for knowledge-work agents lies between domain-level intent and incidental execution mechanics, not between the model and meaning.

Mukul Singh · Director of Science · October 6, 2026

Abstract

As agent loops gain tools, it becomes tempting to make one loop perform every stage of research, analysis, planning, design, simulation, coding, and artifact production. That is capability accumulation, not necessarily good architecture. The durable boundary is a narrow semantic contract: the core agent retains the user’s goal, evidence, hypotheses, domain constraints, and evaluative judgment, while specialized execution paths handle incidental mechanics. This essay develops that “semantic boundary,” uses Office document creation as a revealing concrete case study, tests the thesis against public research, and proposes metrics that could falsify it.

Opening scenario

A strategy becomes an execution-debugging session

Imagine an agent developing a product strategy or a scientific research plan. It has gathered evidence, reconciled conflicting sources, formed a coherent hypothesis, and identified the assumptions that would change the recommendation. Then execution intrudes.

The same loop cleans malformed data, runs a finance or physical simulation, resolves package and version conflicts, refreshes authentication, retries browser actions, and diagnoses rendering or serialization failures. Each step may be necessary, but its traces accumulate: schema exceptions, intermediate tables, environment state, credentials flow, rejected calls, and repair attempts. By the time the loop returns to the strategic question, its original reasoning state is stale and the distinction between durable evidence and transient debugging residue has blurred.

A sufficiently capable model may recover. But recovery is a weak success criterion. The architectural question is why the system allowed the design context to be damaged in the first place.

Good agent architecture should not celebrate recovery from avoidable context damage. It should prevent the damage while preserving the meaning needed for judgment.

The argument concerns where to put a boundary, not whether to build a tiny agent or simply add more agents. Simulation, code execution, data transformation, browser automation, and regulated transaction execution are all candidate specialized runtimes; document and artifact creation is a particularly revealing case because meaning, visual form, application state, and collaboration mechanics meet in one task.

01 · Accumulation

Capability accumulation is not architecture

Modern models can use more tools, sustain longer trajectories, and reason across more modalities than their predecessors. Those gains make a monolithic design technically possible: attach every search system, data pipeline, simulator, code environment, browser, transaction API, artifact primitive, and repair utility to one loop. But “the model can call it” is not an architectural principle.

Every capability changes the loop’s operating environment. Tool descriptions consume attention. Results enter working context. Failures create branches, diagnostics, retries, and stale hypotheses. The effective task can shift from “decide which product bet the evidence supports” to “make that decision while managing a heterogeneous computing environment.” Office APIs, spreadsheet formulas, presentation objects, and file-repair tools are concrete examples of this broader problem, not its definition. Stronger models postpone the pain, but do not eliminate the tradeoff.

Anthropic’s Building Effective Agents recommends starting with the simplest composable pattern and adding complexity only when it earns its place. A June 2026 arXiv survey by Renjun Xu and Yang Yan formalizes agent skills as on-demand packages of instructions, code, and resources, commonly exposed through progressive disclosure. That framing helps explain how specialized capability can remain unloaded until relevant, while the survey’s security and governance discussion cautions that reusable skills also introduce provenance, permission, and supply-chain questions. The important lesson is to make capability loading and delegation responsive to the shape of the work, not to “always use one agent” or “always delegate.”

Two distinct capability patterns matter. An Inline Skill (“teach me how”) loads instructions, examples, code, and resources into the same reasoning loop. The primary agent learns the method and executes it itself, retaining one context, state, and decision path. This fits when the capability can be applied without polluting that loop with a long specialized trajectory. An Agent as Skill (“do this for me”) delegates a complex bounded task to another agent or runtime with its own context, tools, and execution loop. The primary agent supplies a semantic task contract and receives a granular, verifiable return. This fits work that needs isolation, extensive specialized computation, independent exploration, or a separate reliability or security envelope.

Architecture smell

If a loop owns a tool only because it might someday need it, or if it repeatedly re-learns mechanical application behavior while trying to preserve a creative plan, capability has outrun design.

02 · Control condition

The single loop earned its popularity

A single agentic loop paired with a general-purpose container or runtime has been a genuine engineering breakthrough. Give one capable loop code execution, file access, tools, and a persistent workspace, and it gains unusual generality: it can iterate rapidly, preserve continuous context, compose tasks in ways its designers did not enumerate, maintain a unified trace, and avoid much of the integration friction created by delegation.

Leading frontier products have demonstrated that this pattern can handle a surprisingly broad range of knowledge-work and artifact tasks. Anthropic’s simplicity-first guidance and OpenAI’s recommendation to maximize a single agent before adding more loops reflect demonstrated shipping experience, even though they are engineering guidance rather than universal empirical laws. The single-loop container should therefore be the baseline (the control condition) against which a more elaborate architecture must be measured.

The control condition

The single-loop container should be treated as the control condition, not the enemy. It has earned that position through generality and shipping success. The semantic-boundary architecture wins only where measured task performance shows that isolating execution preserves reasoning better than keeping it inline.

A successful default is not automatically the optimum for every task shape. Copying an architecture merely because frontier vendors shipped it is cargo-culting unless the choice is measured against the actual workload. The converse matters just as much: the proposed semantic boundary is an optimization, not a presumption. It must earn the delegation, serialization, observability, and integration complexity it adds.

The Office case study cannot depend on weak APIs, current product gaps, organizational boundaries, or implementation failures. Even if application APIs and low-level tools became nearly perfect, context isolation, least privilege, state ownership, coauthoring semantics, and specialized validation might still justify Agent as Skill delegation. That remains a hypothesis to test. If a better inline tool surface eliminates recovery cost and matches quality, correctness, provenance, and security, the single loop should win.

03 · Working memory

Context is a working memory, not a warehouse

Context quality is not measured only by remaining tokens. A window can be large and still be poor. In the peer-reviewed TACL paper Lost in the Middle, Nelson F. Liu and colleagues showed that access to long context does not imply robust use: performance on their tasks varied with the position of relevant information and was often weakest when that information appeared in the middle. A later Chroma technical report by Kelly Hong, Anton Troynikov, and Jeff Huber evaluated 18 models on controlled tasks while holding task complexity fixed and varying input length; it reported increasingly unreliable and nonuniform performance as inputs grew. The latter is vendor-authored technical evidence, not peer-reviewed consensus, but both results argue against treating context capacity as equivalent to dependable working memory. Four pathologies matter.

Contamination

Material that was locally useful can be globally distracting. A finance trace may be essential to verify a forecast yet harmful to a later typography decision. Mechanical errors are especially contaminating because they generate repeated, superficially salient evidence (exception text, rejected calls, alternate syntaxes) that competes with the durable plan.

Staleness

An agent’s earlier representation of the artifact may no longer match reality after several edits, human coauthor changes, or a repair attempt. Stale object references and summaries make subsequent reasoning precise about the wrong state.

Recovery tax

Compaction and context rebuilding are necessary techniques, but they are lossy. The model must restate goals, recover object identity, rediscover why a choice was made, and verify whether the current artifact still matches the compressed account. Those turns are not free merely because the task ultimately succeeds.

Trajectory length

Each additional action is another opportunity for state drift and tool error. Model quality cannot compensate indefinitely for an interaction layer that makes routine work brittle.

Grounding should therefore follow a “smallest sufficient slice” principle: fetch only the section, range, slide element, or object state needed for the next decision, with stable identifiers and provenance. Context efficiency can then be measured as tokens or bytes retrieved per successful task, not as maximal occupancy of the context window.

Related reading Designing Memory for Enterprise Agents

Applies the same principle to agent memory: load what is certain at session start, retrieve the rest on demand, and reload it after compaction.

The end-to-end token paradox

A clean boundary may add a delegation message yet reduce total tokens. If the delegated runtime completes an operation directly, the system avoids exploratory calls, repeated errors, context reconstruction, and revalidation. A few high-information semantic instructions can be cheaper than a long mechanical trajectory.

04 · Visibility

Why total abstraction also fails

The opposite extreme is equally damaging: hide the artifact behind a vague command surface (“make this slide better”) and return only success or failure. An agent that cannot see slide content, object identity, placement, hierarchy, selection, or the effects of its edits cannot make coherent later decisions. It becomes semantically blind.

A useful representation can expose document content in a model-friendly structure, assign stable identifiers, and support incremental operations against specific elements. The model can then connect a selected phrase to its paragraph, replace one table without regenerating the document, and preserve mappings to the native representation. Long artifacts can expose virtualized structure with on-demand hydration rather than loading everything or hiding everything.

This is abstraction without occlusion. The model does not need character offsets, binary package details, or merge internals. It does need meaningful objects and state transitions. A semantic representation should preserve the things that can change the agent’s judgment: content, relationships, hierarchy, constraints, provenance, and visible consequences.

05 · Definition

The semantic waist

The proposed boundary is a narrow, durable interface between semantic construction intent and mechanical artifact execution. Like the “narrow waist” of a protocol stack, it supports diverse reasoning above and diverse application implementations below without forcing either side to absorb the other’s complexity.

Above the waist, the core loop owns the user’s goal, evidence, narrative, design judgment, and refinement. It decides which numbers are authoritative; what should change; which object is targeted; what must remain invariant; how the update should affect visual hierarchy; and how success should be evaluated.

At the waist, the system expresses fine-grained semantic operations: update the FY26 operating-margin values in chart rev-margin-2; preserve its position and theme; keep the target label emphasized; cite the workbook range used; return changed object IDs, validation results, and a rendered preview. The contract may accept natural language, structured plans, code-like expressions, or mixtures of these. The key is that its nouns and verbs describe the artifact, not the implementation.

A controlled experiment with one kind of contract: typed code DSLs in place of JSON tool calls.

Below the waist, an optimized delegated runtime resolves application interfaces, performs partial reads and writes, maintains session affinity, enforces policy, handles retries, validates rendering and calculation, records provenance, and participates correctly in coauthoring and undo.

This does not remove control from the core loop. It changes the level at which control is exercised. The core still designs, inspects, critiques, and iterates; it simply does not debug the machinery that makes an Office object real.

06 · Architecture

A concrete architecture for knowledge-work artifacts

The architecture combines a single decision owner with progressive context retrieval and an app-owned Agent as Skill execution path. It is deliberately asymmetric: the model receives semantically rich views upward, while the runtime receives constrained operations downward.

The retrieval side begins with compact outlines (headings, slide titles, worksheet and table names) and hydrates precise slices on demand. Read access is least-privilege and read-only by default. Stable IDs connect model-visible objects to application state. The write side applies semantic operations within a live session, returns granular results, and exposes enough state for the core loop to assess the work.

App-owned execution can provide a correctness, fidelity, security, and collaboration envelope that generic file manipulation cannot easily reproduce. Operation-based editing is different from replacing a binary: coauthor-safe editing participates in the application’s revision and session semantics. In this pattern, Inline Skills can teach operation strategy while an app-specialized Agent as Skill owns complex creation and editing through a consistent task-like capability surface.

A typical delegated edit therefore looks less like “rewrite this package” and more like a transaction:

  1. Hydrate the addressed slide, chart, source range, and relevant design constraints.
  2. Submit the intended numerical and visual changes, invariants, and provenance requirements.
  3. Apply operations in the app-owned session; recalculate, render, and validate.
  4. Return changed IDs, semantic diff, warnings, preview, and an undo handle.
  5. Let the core loop inspect the result and decide the next refinement.
07 · Delegation

Teach the loop or delegate the task?

The first design question is whether the primary loop needs to learn a method or receive a completed task. Use an Inline Skill when instructions and resources can improve execution inside one coherent reasoning path. Use an Agent as Skill when a bounded task warrants its own context, tools, execution trajectory, and reliability or security envelope.

The semantic-boundary artifact runtime is an instance of Agent as Skill. The primary loop remains the single owner and writer at the level of meaning: it owns the evidence, narrative, design judgment, constraints, and acceptance criteria. Delegated execution occurs in an isolated loop that owns application mechanics and returns addressable changes, validation, previews, provenance, and undo information. This is neither a thin persona nor an opaque command. Delegation is justified by a semantic and operational boundary.

An Agent as Skill may expose the same task-like interface as an Inline Skill: describe the bounded outcome, relevant objects, invariants, and acceptance criteria; receive a granular result. The primary agent need not reason about transport or orchestration details. A2A is useful here only as a possible interaction and delegation model, not as the identity of the architecture. The durable capability surface is the semantic task contract.

Decomposition is pattern-specific rather than intrinsically “multi-agent.” Microsoft Learn’s February 2026 guidance distinguishes chaining, routing, handoffs, parallelization, orchestrator-worker, and evaluator-optimizer patterns, each with different coordination, state, and observability requirements. OpenAI’s vendor engineering guide similarly recommends maximizing a single agent first, adding multiple agents when complex logic or overlapping tool choices produce persistent failures, and distinguishes manager-led delegation from decentralized handoffs. These are engineering recommendations, not universal empirical laws, but they clarify that adding loops creates design obligations rather than removing them.

A fresh industry signal: DeepSeek Harness

DeepSeek Harness is an open-source agent harness in developer preview, with explicit warning that compatibility-breaking changes will occur. Its stated principle is “everything is a plugin,” powered by Cordis: even the model adapter, tool registry, session log, and agent loop are replaceable through configuration. The repository separates capability seams for skills, subagents, workflows, compaction, request context, sandboxing and guardrails, tools, filesystem, shell, web, persistent sessions, approvals, and telemetry. Each seam distinguishes a Service Definition, Service Provider, and Consumer; subagent Providers can range from a fresh child agent to a delegated turn in another product.

This reinforces the vocabulary here rather than collapsing it. An Inline Skill can enter the primary loop through a skill capability, while an Agent as Skill can use the subagent seam to own a separate trajectory and return a granular result. A connector Consumer may expose a model-facing task while its Provider owns authentication, execution, retries, policy, and result normalization. Complex connector workflows can therefore be delegated without permanently contaminating the primary loop with connector mechanics; this is an architectural implication, not a claim that DeepSeek ships enterprise connectors.

The design does not simply argue for more agents. Because the loop itself is replaceable, tools pass through a guarded execution pipeline, processes can be confined through sandbox backends, and capability sets can be composed per agent or session, one loop remains a valid control condition and delegation remains task-dependent. Its append-only session event log is the source of model context: model-visible inputs must be logged and reconstructable, supporting replay, resume, transcripts, telemetry, and observability.

That distinction reconciles apparently conflicting public evidence. Anthropic reported a 90.2% improvement on an internal research evaluation for its multi-agent research system, while also reporting roughly 15 times the token use of ordinary chat. The system works because breadth-first reading decomposes into independent searches across separate contexts. Yet final synthesis remains unified. Harrison Chase summarizes the practical rule: reads parallelize better than writes.

Cognition’s Don’t Build Multi-Agents emphasizes the cost of dispersed interdependent decisions and partial context. MAST, the NeurIPS 2025 study by Cemri and colleagues, catalogs specification, misalignment, and verification failures and finds that multi-agent gains are often limited. These critiques apply directly to coupled artifact writing: two writers changing layout, narrative, and object state in parallel will make implicit decisions that collide.

The semantic-boundary architecture therefore uses a single writer at the level of meaning. Independent evidence gathering can fan out. Mechanical execution can be delegated to an Agent as Skill because it is constrained by addressed semantic operations and granular verification. But decisions that jointly shape the artifact (story, visual hierarchy, terminology, and tradeoffs) remain in one continuous reasoning thread.

Delegation test

Ask first: does the primary loop need to learn the method, or delegate the completed task? Delegate when the work can be specified by a stable semantic contract and verified from a granular return, not merely because a role label sounds specialized.

Security strengthens the case for a deliberate boundary. Simon Willison’s “lethal trifecta” (private data, untrusted content, and external communication) warns against combining broad authority in one exposed agent. The delegated artifact runtime should receive only the files, operations, and network posture it needs. Read-only grounding should be separate from explicit writes, with audit and policy enforcement at the boundary.

08 · Evidence

Evidence and falsifiable predictions

The semantic boundary is an architectural hypothesis, not a universal law. Current evidence supports testing it, but does not settle every implementation choice. The baseline comparator is an optimized single-loop container using the best available Inline Skills and tools, not an intentionally weak monolith.

External evidence

Public research provides directional support. Peer-reviewed long-context work shows that nominal access is not dependable use; a vendor technical report extends that concern across controlled increases in input length. Simplicity-first vendor guidance cautions against gratuitous orchestration, while Microsoft’s pattern catalog makes the associated coordination, state, and observability requirements explicit. Multi-agent research shows substantial gains where independent reading can exploit separate contexts, but with high token cost. Cognition and LangChain identify continuous context and the read/write split as critical. MAST shows that coordination and verification are recurring failure classes. An arXiv survey describes progressive disclosure as a way to keep inactive capability out of working context while emphasizing skill security and governance. Least privilege limits the blast radius of tool use.

DeepSeek is developer-preview architecture evidence and currently does not establish measured performance gains for subagents; its BENCHMARK.md provides only basic instructions for independent tasks.

Matched experiments and predictions that could prove the design wrong

Evaluation should compare two matched conditions: a single loop with optimized inline skills and tools, and a semantic-boundary system using Agent as Skill delegation. Experiments should control for model, task, allowed information, and, where possible, compute and token budget. Delegation overhead and loss of useful cross-boundary context are real costs and must be counted rather than explained away.

Compared with that single-loop baseline on matched knowledge-work tasks, a semantic-boundary system should:

  • increase end-to-end success rate and independently judged output quality;
  • reduce total tokens per successful task despite delegation overhead;
  • reduce recovery turns and error-repair time without unacceptable wall-clock latency;
  • improve semantic edit fidelity, state and coauthor correctness, and cross-client rendering correctness;
  • increase provenance coverage while reducing security exposure.

If these gains do not appear, or if the contract repeatedly omits information needed for judgment, the boundary is misplaced. If delegation latency and serialization dominate without reducing recovery, it is too expensive. If the core loop cannot understand why an edit changed the artifact, it is too opaque. If the delegated runtime requires the core to specify application internals, it is too low-level.

09 · Practice

Design principles and decision checklist

  • Preserve meaning, hide mechanics. Expose content, identity, hierarchy, constraints, selection, and edit effects; conceal package and API trivia.
  • Use the smallest sufficient context. Start with outlines; hydrate addressed sections, ranges, and objects on demand.
  • Prefer stable identifiers. Names and IDs should survive reordering and incremental edits without inviting the model to infer false structure.
  • Make edits operation-based. Express insert, replace, move, restyle, recalculate, and annotate against anchors instead of replacing the whole file.
  • Keep one semantic writer. Parallelize independent reads; serialize coupled decisions and writes.
  • Choose how capability enters the system. Ask whether the primary loop needs to learn the method through an Inline Skill or delegate the completed task to an Agent as Skill.
  • Return granular evidence. Include changed IDs, diffs, previews, validation, provenance, warnings, and undo handles.
  • Separate read and write authority. Ground read-only by default; make writes explicit, scoped, policy-aware, and auditable.
  • Optimize model and harness jointly. Treat recurring tool errors as environment defects, not only prompting failures.
  • Measure recovery as well as completion. A task that succeeds after wandering may still reveal a poor boundary.

10 · Conclusion

Hide irrelevant mechanics without hiding meaning

Agent systems will continue to gain capabilities, and powerful models will keep moving the best boundary. Sometimes improved models and inline tools will correctly collapse a layer into the core loop; sometimes isolation will still produce better results. The boundary is empirical and movable, not ideological.

For knowledge-work artifacts, the most promising durable boundary is semantic construction. The core agent should see and control the things that matter to judgment: the content, evidence, objects, relationships, constraints, intended effects, and visible results. It should not have to reason through the incidental mechanics of constructing, repairing, recalculating, securing, or coauthoring the file.

The semantic waist is narrow but expressive. Above it, reasoning remains coherent and accountable. Below it, specialized runtimes can evolve with application internals, performance requirements, and collaboration semantics. Between them, stable IDs, incremental operations, and granular returns preserve agency without exposing machinery.

The claim is testable: against an optimized single-loop control, this boundary should produce better artifacts with fewer recovery turns, lower end-to-end cost, stronger provenance, safer authority, and more reliable editing. If it does not, revise or remove the boundary. Architecture is less the act of hiding complexity than the discipline of deciding, by evidence, which complexity each part of the system must understand.
